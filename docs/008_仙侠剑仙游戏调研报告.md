## 0. 结论先行

**建议做一款单机优先、数据驱动的“双相循环”游戏：**

> 大地图御剑游历（步行/飞行、多角度） → 遭遇战切入伪 3D 空间 RTS（小队、远程/区域法术、妖兽/修士/神兽） → 战利品回流宗门（功法、炼丹、炼器、符箓） → 境界突破解锁新能力与新区域 → 再出发。

**核心差异化不是“又一个修仙模拟器”，而是三件事的耦合：**

1. **御剑飞行是真玩法**：高度层、速度、视野、越地形能力都参与探索与战斗，而不是纯坐骑皮肤。
2. **战斗层继承 fighter 的空间战术手感，但表现层改为混合方案**：真 3D 舞台 + 3D 空间中的切片体单位 + GPU 法术特效（详见 §5.6）；不把 Web 端的实现约束当成设计原则。
3. **宗门层不是菜单，而是战力来源**：丹药/法器/符箓/功法直接改变战斗层的技能槽与数值，形成可感知闭环。

**引擎建议：Godot 4.7.2 作为生产引擎；Web/Canvas2D 作为快速验证原型。**

- 本机已实机确认 Godot 4.7.2：`E:\dev\godot\Godot_v4.7.2-stable_win64.exe`，且 PATH 中存在 `/e/Dev/Godot`（沿用 docs/002 探针结论）。
- Godot 4.7.2 **没有内置 WebView**，`.ts` 无 loader，不能直接加载 fighter 的 React/TypeScript 源码（沿用 docs/002）。
- 因此不要幻想“把 fragment 塞进 Godot”。正确做法是：**Web 端复用源码验证手感，Godot 端按同一渲染思想重写核心战斗层**。
- 若先走 Android，可用 `docs/004` 的 Capacitor 方案包装 Web 原型；长期仍建议回到 Godot 原生导出。

### 2.2 竞品空白 = 本项目机会

现有产品普遍落在两个极端：

- **鬼谷八荒 / 觅长生**：重个人成长与大地图，但战斗是 2D 弹幕或策略组合，缺少“空间站位 + 高度 + 队友协同”的战术层。
- **了不起的修仙模拟器**：重宗门系统引擎，但玩家更多是调度者而不是踩剑冲阵的剑仙。
- **碧海苍云录**：把“手动御剑探索”做进手游，但战斗仍是 3 人回合制 + 挂机刷词条，缺空间战术与宗门生产回流。

**空白点：** 把“剑仙本人在场”的空间战斗，与“宗门作为后台供给”的经营系统放进同一个循环。  
玩家既能御剑冲进山海经战场，也能回山门决定下一炉丹、下一枚符、下一门功法。

### 2.4 补充竞品：《碧海苍云录》与本次遗漏复盘

> 用户对本报告打回：“调研没有包含碧海苍云录”。经澄清，这是**报告遗漏竞品**的批评，不是要求调研该游戏的玩家差评。本节为补充。

#### 2.4.1 为什么它应该进竞品池

《碧海苍云录》（TapTap app 324395，S27）是**移动端水墨修仙刷宝 RPG**，与本项目 G1/G5 高度重合：

- 官方简介明确写“脚踏飞剑自由探索”，并强调“不是点击某个按钮，而是需要玩家亲自操作角色脚踏飞剑飞来飞去，开启传送点，与 NPC 对话，与怪物战斗”；
- 水墨国风 + 山海经神话参考；
- 无抽卡，伙伴/法宝通过主线、副本、任务获取；
- 离线挂机收菜 + 手动刷随机词条装备；
- 炼气→大乘多阶境界，境界突破解锁功法槽与飞行特效（S28/S29）。

它与前四个 Steam 竞品形成关键互补：**它证明“手动御剑探索”在移动端也能作为核心卖点**，而且是用“无抽卡 + 离线挂机 + 词条刷宝”承接长线留存，而不是靠重剧情或重模拟。

#### 2.4.2 对本项目的可借鉴点

| 可借鉴 | 具体做法 |
|---|---|
| 御剑探索的真实操作感 | 大地图不只有点击寻路；保留手动御剑、传送点解锁、路上遭遇 |
| 长线保值装备 | 词条转移、装备无损升阶，避免“刷到新装备旧投入清零” |
| 无抽卡信任感 | 队友/功法/法宝可通过玩法获得，付费只卖便利或外观 |
| 双节奏 | 离线收菜保底 + 手动高难副本提供深度 |

#### 2.4.3 需要规避的坑（来自玩家反馈，非本报告主体差评调研）

S28/S29 的玩家讨论集中反映：

- **成就空心化**：达到境界本身不带来足够变化，“境界到了又不能怎么样”；
- **作业感**：副本越来越多，零氪每日清本时间越来越长，缺扫荡；
- **节奏拖沓**：爬塔不能跳过、二倍速仍要硬等；
- **系统解锁错位**：6 阶装备都穿上了，锻造任务才开放且只能做 1-3 阶；
- **定位失衡**：灵根/道途/职业收益与投入不匹配。

对应到本项目的设计约束：

1. **境界突破必须同时改战斗动词、地图可达性、宗门权限**（已在 §4.1 写入）；
2. **重复战斗必须有可跳过/扫荡/倍速**，但核心遭遇保持手动；
3. **系统解锁时机对齐装备/境界阶段**，不要让系统变成迟到的奖励；
4. **配队定位要有不可替代价值**，避免“氪了/养了也不如野路子”。

#### 2.4.4 遗漏根因与举一反三

| 问题 | 根因 | 修正动作 |
|---|---|---|
| 漏掉《碧海苍云录》 | 竞品检索过度偏向 Steam/PC 官方商店页和高热度关键词（仙侠/修仙/宗门/炼丹），没有覆盖 TapTap/App Store 手游赛道 | 后续竞品检索必须同时覆盖 PC 与移动端平台 |
| 只按“玩法标签”找竞品 | 未把“用户心中的同类产品”作为输入；未搜“御剑飞行/无抽卡/刷宝/词条/挂机”等长尾词 | 增加长尾关键词矩阵；先向用户收集“你心中的竞品名单”再收敛 |
| 没有口碑维度 | 只抄官方卖点，没有看玩家实际抱怨 | 每个重点竞品必须同时记录“官方卖点 + 玩家吐槽 + 对我方启示” |
| 单一轮检索即定稿 | 缺竞品清单复核环节 | 报告定稿前输出候选清单让用户确认，避免自说自话 |

## 3. 产品核心循环设计

### 3.1 双相循环（推荐主循环）

```text
[宗门相] 学功法 / 炼丹 / 炼器 / 画符 / 接任务
        │  产出：技能槽、丹药、法器、符箓、队伍配置
        ▼
[大地图相] 步行或御剑；切换视角；发现 POI / 妖兽 / 秘境 / 敌修
        │  触发：EncounterSpec（地形、种子、参战者、天气）
        ▼
[战斗相] 伪3D空间 RTS：小队指挥、远程剑诀、区域法术、高度差
        │  产出：BattleResult（战利品、经验、声望、世界标记）
        ▼
[结算回流] 宗门材料入库 → 新配方/新境界 → 回到宗门相
```

### 3.2 一次 10 分钟游玩的理想节奏

| 阶段 | 玩家动作 | 系统反馈 |
|---|---|---|
| 0-2 min | 在山门接到“北溟妖兽扰灵田”任务，选择带 2 名队友、3 张雷符 | 任务板标记地图 POI，背包扣除符箓占位 |
| 2-4 min | 御剑飞越云海，切换 45°/70° 视角找山谷入口 | 飞行消耗灵力；高处视野更远但更易被发现 |
| 4-7 min | 进入战斗：队友牵制，玩家远程剑诀 + 雷池区域法术 | 妖兽冲锋、敌修放符；地形阻隔与高度差生效 |
| 7-9 min | 击败妖兽，捕获材料，队友受伤 | 掉落妖丹、鳞片；队友状态带入结算 |
| 9-10 min | 回宗门炼丹，突破筑基，解锁“御剑斩” | 新技能进入战斗技能栏；地图解锁新区域 |

## 4. 系统拆解

### 4.1 境界系统：不是数值，而是“动词解锁”

推荐首版 5 阶，名字保留用户要求的练气/筑基/金丹/元婴，再加化神作为阶段目标：

| 境界 | 战斗解锁 | 探索解锁 | 宗门解锁 | 叙事身份 |
|---|---|---|---|---|
| 练气 | 基础走位、低阶符箓、1 个远程剑诀 | 只能步行；低空异常不可进 | 外门弟子；基础丹房 | 凡人修士 |
| 筑基 | 飞剑连击、短距突进、护体罡气 | 御剑低空；可越浅山 | 内门弟子；可接地阶任务 | 真正修士 |
| 金丹 | 区域法术（雷池/火域）、金丹法宝 | 御剑高空；云海/海面可通行 | 执事；可开炉炼制中阶丹 | 一方强者 |
| 元婴 | 元婴出窍（分身/远距离观察）、瞬移剑 | 跨区域快速飞行；秘境入口 | 长老；可授徒、开宗门大比 | 宗门柱石 |
| 化神 | 领域展开、神兽契约、剑阵 | 地图边界扩展；天气免疫 | 宗主候选 | 传闻级人物 |

**设计规则：**

- 每次突破必须同时改变**战斗动词 + 地图可达性 + 宗门权限**，否则玩家感受不到境界。
- 突破要有代价：灵石、丹药、时间、心魔/天劫风险至少取其二。
- 境界差不要像 carefree 那样做 10→100→1000 的指数伤害；推荐乘数 1.0 / 1.4 / 2.0 / 2.8 / 4.0，靠机制而非纯数值拉开差距。

### 4.2 战斗层：伪 3D 空间 RTS

沿用 fighter 的已验证技术思想（docs/002、docs/006）：

- 低分辨率帧缓冲 + `putImageData` + `image-rendering: pixelated`；
- 体素切片 sprite-stack 表达体积；
- `pixelSize` 作为清晰度/性能主旋钮；
- `bloom/grain/vignette` 控制“软/脏”的观感；
- `spread` 只调切片间距，过大导致机身散架，**不是清晰度旋钮**。

#### 坐标与高度层

```text
地面平面：X/Z
高度轴：  Y（altitude）
高度层：  GROUND / LOW_AIR / HIGH_AIR / SKY
```

- 单位有 `position: Vector3` 与 `altitude_layer`。
- 法术有 `target_layer` 与 `radius`：雷池打 GROUND，剑气可打 LOW_AIR，神兽冲击波可跨层。
- 山体/海面不是背景，而是导航与命中约束：山阻挡低空弹道，海面减速地面单位但利于神兽。

#### 相机预设

| 预设 | 俯角 | 用途 |
|---|---|---|
| 战术俯视 | 70° | 看清单位站位、法术范围边界 |
| 标准战斗 | 45° | fighter 主视角，兼顾体积感与可读性 |
| 剑仙追尾 | 25° | 御剑冲锋、飞剑特写、过场演出 |

切换必须是**同一战场、同一状态**，不是三段独立动画。

#### 战斗单位类型

| 类型 | 行为 | 威胁 |
|---|---|---|
| 队友 | 跟随、集火、保护、被击倒可救 | 资源与情感投入 |
| 猛兽 | 直线冲锋、扑击、畏惧火/雷 | 近场压迫 |
| 人类敌人 | 放符、走位、集火玩家 | 远程反制 |
| 神兽 | 阶段化 Boss，跨层攻击，地形互动 | 高潮体验 |
| 玩家剑仙 | 飞行 + 剑诀 + 区域法术 + 指挥 | 核心动词载体 |

#### 法术分类（首版 6 个足够）

1. **弹道剑诀**：单体，低前摇，低耗灵；
2. **区域法术**：圆/扇形，持续 tick，改变地面状态；
3. **护体罡气**：短时减伤/反弹；
4. **瞬移剑**：位移 + 路径伤害；
5. **符箓爆发**：宗门产出，一次性高威力；
6. **法宝领域**：金丹以上，持续区域增益/压制。

### 4.3 大地图：步行 / 御剑 / 多角度

推荐 **分区块高度场 + POI 图**，而不是首版无缝全球：

- 每块地图有 `biome`、`heightmap`、`poi[]`、`spawn_rules[]`、`weather[]`；
- 步行：走导航网格，速度慢，可采集；
- 飞行：忽略部分地面障碍，消耗灵力，视野半径增大；
- 切换视角时，UI 与寻路目标保持世界坐标一致。

### 4.4 宗门系统：让生产影响前线

首版只做四条生产链，够形成闭环：

| 链 | 输入 | 输出 | 战斗影响 |
|---|---|---|---|
| 炼丹 | 灵草 + 妖丹 + 炉火 | 突破丹 / 疗伤丹 / 灵力丹 | 突破门禁、续航 |
| 炼器 | 矿石 + 妖兽材料 | 飞剑 / 护甲 / 法宝 | 改技能与属性 |

- 高级材料只在特定境界区域掉落；

- 丹药有耐药性，符箓有携带上限；
- 宗门建筑提供产能上限，避免无限刷。

### 5.5 渲染复用策略

**Web 原型 → Godot 生产 的迁移边界：**

| 可复用 | 需重写 |
|---|---|
| 战斗手感参数（pixelSize/spread/bloom） | React 组件树 |
| 切片模型数据（体素层数组） | Canvas2D 帧缓冲 |
| 法术形状/时间轴设计 | WebGL 尾焰 shader（改为 Godot ShaderMaterial） |
| 输入映射与相机预设 | `putImageData` 路径 |

Godot 里建议两种实现路线二选一：

1. **SubViewport + CanvasItem 层**：最贴近 fighter，先做出来；
2. **MeshInstance3D/MultiMesh 切片面片**：更利于相机多角度与 3D 排序，生产更稳。

建议：**P0 用路线1 做手感验证；它只是原型手段，不代表生产架构。生产架构见 §5.6 复议。**

### 5.6 架构复议：既然生产引擎是 Godot 3D，为什么还谈 sprite-stack？

> 触发：用户质疑「既然都走 3D 了，为什么不走真 3D 还要 sprite-stack？」
> 结论：**原 ADR-2 论证不足，此处修正。** 质疑成立的部分要认，不能拿"复用已有技术"当挡箭牌。
> **用户决策（2026-11-17 14:02）：确认采用路线 B。** 详细实施规格见 `docs/009_路线B实施规格.md`。

#### 5.6.1 原论证的问题

原 ADR-2 写："战斗层保留伪 3D sprite-stack，不上全 3D，理由是复用已验证视觉语言与性能边界"。这有三处站不住：

1. **把约束当原则**：fighter 用 sprite-stack 是因为它是 Web 端 Canvas2D 软件光栅化，根本没有 GPU 3D 管线（只有尾焰蹭了点 WebGL）。这是"没得选"，不是"选得好"。
2. **混淆两层决策**："用 Godot 3D 引擎"和"单位必须是 3D 网格"是两件事。选 Godot 拿到的收益（Android 导出、NavigationAgent3D、MultiMesh、HLOD、资源/信号系统）与单位怎么画无关。
3. **与 G5 冲突**：预渲染切片只在特定俯角好看，相机一转就露出纸片侧面。用户明确要"可切换多角度"，纯 CanvasItem 层无法满足。

#### 5.6.2 三层澄清

| 层 | 决策 | 说明 |
|---|---|---|
| **L1 引擎层** | Godot 4.7.2，真 3D 引擎 | 拿到的是导出/导航/物理/数据/信号，与单位表达方式无关 |
| **L2 场景/空间层** | **真 3D**：高度、透视、山、海、云、光照、可转相机 | 满足 G2「山、海」与 G5「多角度」 |
| **L3 单位表现层** | 这才是"切片 vs 真 3D 网格"的真正战场 | 原报告把 L2 和 L3 混为一谈 |

#### 5.6.3 三条路线对比

| 路线 | 舞台 | 单位 | 优点 | 代价 | 适用条件 |
|---|---|---|---|---|---|
| **A 纯真 3D** | 3D | 低模网格 + 骨骼 + PBR | 相机 360° 无死角；光照阴影自然；近景演出空间大 | **需要成套 3D 美术资产**（当前最大缺口）；骨骼、蒙皮、LOD、面数都要管 | 有稳定 3D 美术产能，且要做角色特写/过场 |
| **B 混合（修正后推荐）** | 3D | 3D 空间中的切片体/体素：`MeshInstance3D` + `MultiMesh` 承载多层切片，随相机 billboard | 保留国风切片美术与已有资产；相机可转；深度/遮挡交给引擎；性能可控 | 要写切片组装与 billboard；俯角仍需限制，近距离侧面会露馅 | **当前阶段**：美术资产少、要先出玩法切片、又想要真 3D 相机 |
| **C 原 sprite-stack** | 2D CanvasItem | 2D 切片 | 最贴近 fighter 源码 | 放弃引擎 3D 能力，等于白选 Godot 3D；与 G5 冲突；换网页封装结果一样 | 只做 Web/Android 且永久锁定单一俯角 |

#### 5.6.4 修正后的推荐：路线 B

- **地形 / 山 / 海 / 云 / 光照 / 相机** → 真 3D。NavigationAgent3D 直接用于地面与低空单位（`use_3d_avoidance` 处理飞行层）。
- **单位** → 多层切片不再是 Canvas2D 图层，而是 3D 空间里的 `MeshInstance3D` / `MultiMesh` 实例，参与真实深度排序与遮挡，按相机 billboard。fighter 的体素切片数据可转成网格，资产不浪费。
- **法术 / 剑光 / 尾焰** → GPU 粒子 + `ShaderMaterial`，比软件光栅更适合区域法术和大场面。
- **远景** → HLOD / billboard / impostor（S25 官方推荐）。
- **数据层** → `UnitDef` / `SpellDef` 不变；将来有 3D 美术时，单位可平滑替换为真网格，接口不动。

**相机约束（路线 B 的关键）**：不做 360° 自由旋转，做"有限俯角 + 平滑轨道"——25°/45°/70° 三档，左右各 60°  orbital。既满足"可切换多角度"，又不让切片从侧面露馅。

#### 5.6.5 什么时候应该直接上真 3D 网格

当以下三条**同时**满足时，sprite-stack 应整个放弃，走路线 A：

1. 有稳定的 3D 美术产能（或预算）；
2. 要做近景剧情演出 / 角色特写 / 过场动画；
3. 目标平台是中高端 PC / 主机，而非低端 Android。

#### 5.6.6 一句话

**sprite-stack 不该是"引擎选了 3D 所以单位要不要也 3D"的信仰问题，而是"在还没有 3D 美术资产时，如何既吃到 3D 引擎的相机/空间/光照，又不必凭空变出一套模型"的资产过渡策略。** 它是路线 B 的起点，不是终点。

## 7. 风险与对策

| 风险 | 表现 | 对策 |
|---|---|---|
| 范围爆炸 | 想同时做开放世界、宗门模拟、RTS、语音 NPC | 首版锁死 5 境界 / 1 山区 / 1 海域 / 1 宗门 |
| 伪3D 可读性差 | 切片散架、法术范围看不清 | 限制 `spread`；区域法术加地面投影圈；用 docs/006 参数基线 |
| 飞行破坏关卡 | 直接飞过所有障碍 | 灵力消耗、高空被发现概率、部分秘境仅低空可进 |
| 经济通胀 | 丹药符箓无限刷，突破无意义 | 材料境界门禁 + 携带上限 + 失败损耗 |
| 单位性能 | 大量法术 tick + 寻路卡顿 | 空间哈希；NavigationAgent 降频；MultiMesh；区域法术批量结算 |
| 多平台分裂 | Web 与 Godot 两套代码漂移 | 只共享**数据表与参数**，不共享 UI 代码；各端各自最优 |
| 美术风格漂移 | 水墨、像素、赛博混搭 | 定调：水墨写意 + 克制像素；禁用霓虹赛博色 |
| LLM 依赖 | 延迟、成本、内容不可控 | MVP 不用；后期做可选 NPC 对话插件 |

### 7.1 清晰度与观感基线（沿用 docs/006）

- 桌面：`pixelSize:1, bloom:0.4, grain:0, vignette:0.15, jetScale:0.8`
- 移动：`pixelSize:2, grain:0, bloom:0.4`
- 原则：先保帧率，再谈锐化；`grain` 一律关。

### 7.2 Android 路径（沿用 docs/004）

若想在 Godot 完成前先摸手机：

- Web 原型用 Capacitor 包装；
- 关键配置：`appId`、`appName`、`webDir`、`android.allowMixedContent=false`、`zoomEnabled=false`、`minWebViewVersion=60`；
- 触屏沿用 fighter 已有的 `pointer: coarse` 思路：单指转向、轻点翻滚、屏幕按钮；
- 移动端优先 `pixelSize:2`。

### 7.3 环境探测复盘（沿用用户纠正后的规则）

任何“工具不存在”的判断，必须三重确认：

1. 读环境清单（`C:\src\CTF\环境清单.md` 等）；
2. 枚举 PATH 目录 + 文件名 glob；
3. 实机运行 `--version`。

不得只用 `command -v godot`。本机 Godot 文件名是 `Godot_v4.7.2-stable_win64.exe`。

### 7.4 LLM NPC 的定位

开源项目 S22 展示了 LLM 驱动 NPC 的可能性，但建议定位为**后期可选增强**：

- 可增强：宗门弟子闲聊、奇遇文本、战斗小剧场；
- 不可依赖：任务发放、经济结算、境界突破规则；
- 原因：可控性、延迟、离线可玩性、内容审查都更适合规则系统打底。
